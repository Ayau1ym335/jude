# Blockers & Known Limitations

## GEO-001: Производительность pygeodesic на крупных сканах (> 100k граней)

**Статус:** Известное ограничение  
**Обнаружено:** Неделя 6 (Фаза 2)  
**Планируемое решение:** Неделя 10

### Описание

Алгоритм `PyGeodesicAlgorithmExact` (реализация алгоритма Дейкстры-Митчелла-Маунта) имеет
квадратичную сложность по числу вершин. При работе с реальными сканами стопы
(типичный размер: 50 000–500 000 граней) время вычисления может превысить
допустимый порог в 3 секунды.

### Измерения (локальная машина, CPU-only)

| Mesh (вершин / граней)  | Время геодезического пути |
|-------------------------|---------------------------|
| icosphere × 1 (642 / 1280) | ~0.01 с |
| icosphere × 5 (10 242 / 20 480) | **0.82 с** |
| Типичный скан стопы (~100k+ граней) | TBD — файл в Storage недоступен |

> **Примечание:** Единственный скан в базе данных (`ce0590f6-…`) имеет файл
> `disk (2).stl`, который отсутствует в Supabase Storage (Storage 404).
> Фактическое время на реальном скане стопы не замерено.
> Эндпоинт возвращает HTTP 502 за 2.77 с (всё время — сетевой запрос к Storage).

### Риски

- На сканах > 200k граней время вычисления может превысить 3 с (таймаут Uvicorn по умолчанию — 30 с).
- Блокирующий вызов в async-эндпоинте (`async def geodesic_curve_endpoint`) — пока приемлемо.

### Планируемые решения (Неделя 10)

1. **Decimation перед геодезическим вычислением** — упростить mesh до ~50k граней через `trimesh.simplify_quadric_decimation`, сохраняя топологию.
2. **`asyncio.run_in_executor`** — вынести вычисление в thread pool, чтобы не блокировать event loop.
3. **Кэширование алгоритма** — хранить инициализированный `PyGeodesicAlgorithmExact` на период сессии.

## GEO-002: Файл скана недоступен в Supabase Storage для E2E-тестирования

**Статус:** Разрешено (используется скрипт seed_test_scan.py)  
**Обнаружено:** Неделя 9  
**Решение:** Разработан скрипт `backend/scripts/seed_test_scan.py`, который генерирует тестовый `.stl` (icosphere), загружает его в Storage (используя service key) и создаёт пациента, скан и проект, обходя ошибки. Это разблокировало E2E-тестирование геодезической кривой на клиенте.

### Описание

Единственный скан в БД (`ce0590f6-…`) ссылается на файл
`4cdc0cc3-…/disk (2).stl` в бакете `scan-files`, который возвращал HTTP 404.
Из-за этого:

- Backend `load_mesh_from_url` выбрасывает `StorageApiError`
- Frontend viewer не может загрузить 3D-модель (падает на `supabase.storage.from("scan-files").download(...)`)
- E2E-прогон (клик → кривая → отображение) невозможен до появления рабочего скана

### Workaround

Dev-компоненты (`RaycastTest`, `GeodesicCurveTest`) реализованы и подключены
к viewer-странице. Они активируются автоматически при `NODE_ENV=development`.
Для теста достаточно:
1. Загрузить любой `.stl`-файл через `/upload`
2. Открыть страницу проекта с рабочим `scan_id`

### Архитектурные замечания

- Реализован нативный Three.js raycasting (не `@react-three/fiber`, т.к. стек проекта — ванильный Three.js).
- `ModelViewer` экспортирует `getMesh()`, `getCamera()`, `getRenderer()` через `useImperativeHandle`.
- Кривая рисуется через HTML5 Canvas overlay (не в 3D-сцене) с перепроекцией через `Vector3.project(camera)`.
- Overlay перерисовывается каждый `requestAnimationFrame` для корректного отображения при вращении камеры.

## GEO-003: Drag опорных точек в нативном Three.js стеке

**Статус:** Реализовано (Неделя 10, с оговорками)  
**Обнаружено:** Неделя 10  

### Что испробовано

Задача предлагала подход через `<Sphere onPointerDown>` из `@react-three/drei` (R3F).
**Это несовместимо с нашим стеком** — проект использует нативный Three.js без R3F/Drei.

Реализован альтернативный нативный подход:

1. `pointerdown` на `renderer.domElement` → проверяем расстояние в 2D между курсором и 2D-проекцией каждой точки (радиус захвата `DRAG_HIT_RADIUS = 14 px`)
2. При попадании: `setPointerCapture(pointerId)` на canvas (событие не уходит в OrbitControls), `setControlsEnabled(false)` — орбита заморожена
3. `pointermove` → синхронный `raycastSync()` к mesh-у → обновляем позицию точки немедленно (ref + setState для RAF-loop)
4. `fetchCurve` дёргается с debounce 250 мс — API не получает запрос на каждый пиксель
5. `pointerup` → снимаем capture, включаем controls, финальный `fetchCurve()`

`pointerDownOnPointRef` разделяет «начало drag» от «простого клика для добавления точки».

### Известные ограничения (оставлено в MVP)

| Ситуация | Поведение |
|----------|-----------|
| Быстрое движение мышью за край mesh | raycast промахивается → точка остаётся на последней позиции (не «слетает») |
| Drag без рабочего бекенда | Точка двигается визуально, кривая не пересчитывается (debounce + отсутствие ответа) |
| Touch-устройства | `setPointerCapture` работает, но не тестировалось |

### Как тестировать

1. Открыть `/projects/{project_id}/viewer`
2. Нажать **✏️ Линия**, поставить 2–3 точки
3. Навести курсор на существующую точку (жёлтый круг) — размер увеличится до `DRAG_HIT_RADIUS * 2`
4. Зажать мышку и потащить — точка перемещается по поверхности, кривая пересчитывается
5. Отпустить — финальный запрос кривой
